# Game Design Document

**Go Idle Game - Roguelike Incremental Developer Simulator**

Version 1.0 | Last Updated: 2025-01-02

---

## Overview

A deep incremental idle game where players build and grow a software company. Core mechanic: **roguelike upgrade draws with strategic trade-offs**. Each run features random upgrades that force players to adapt their build strategy. The game emphasizes planning, resource management, and decision-making under uncertainty.

**Core Philosophy**: Not just "buy the next thing" - players must think critically about build synergies, tech debt management, and long-term efficiency.

---

## Resource Economy

### Three-Tier Resource System

**Primary Currency: Lines of Code (LOC)**
- Generated manually via SPACE key (timer-based) or passively from Code Editors
- Base generation rate: Manual coding produces 1 LOC every 5 seconds
- Used to purchase buildings and draw upgrades

**Secondary Resource: Features**
- Built with LOC (conversion rate TBD)
- Generate Users passively over time
- Key measurement of progress

**Tertiary Resource: Users**
- Generated by Features
- Determines prestige rewards
- Unlocks meta-progression

**Resource Flow:**
```
Manual Input / Code Editors → LOC
LOC → Buildings (production) / Upgrades (buff multipliers)
Buildings → Features (automatic)
Features → Users (automatic)
Users → Prestige Currency (on prestige)
```

## Buildings System

### Core Mechanics

**Storage**: Count-based storage (not individual instances)
- Each building type tracked as `{Count, Name, ProductionRate, Cost}`
- Simple, efficient for incremental gameplay

**Cost Scaling**: Very slow exponential growth
```
Cost = BaseCost * (CostMultiplier ^ Count)
```

**Example with Code Editor (BaseCost: 10, Multiplier: 1.08)**:
- Purchase 1: 10 LOC
- Purchase 2: 10.8 LOC
- Purchase 3: 11.7 LOC
- Purchase 10: 21.6 LOC
- Purchase 50: 47.0 LOC
- Purchase 100: 99.9 LOC

Multipliers range from 1.08 (very gradual) to 1.12 (moderate), preventing exponential explosion while still requiring strategic planning.

**Production Scaling**: Slow logarithmic dampening
```
Total Production = BaseProduction * Count * (1 + log(Count + 1))
Per-Building Efficiency = BaseProduction * (1 + log(Count + 1))
```

**Example with Code Editor (BaseProduction: 0.1 features/s)**:
- 1 building: 0.17 features/s total (0.17x per building)
- 10 buildings: 2.4 features/s total (0.24x per building)
- 100 buildings: 36 features/s total (0.36x per building)

**Why Logarithmic?**
- Prevents single-building strategies from dominating
- Encourages diversification ("I need to buy new building types")
- Makes upgrades more valuable ("I need upgrade X to fix my scaling")
- Creates natural endgame ("this building is tapped out, time for prestige")

## Upgrade Shop (Core Mechanic)

### The Draw System

**Mechanics**:
- Single button: "Draw Upgrade" (or assigned key)
- Each draw costs exponentially increasing LOC
- Cost progression: 5 → 12 → 30 → 75 → 188 → 470 → 1175... LOC
- Formula: `NextCost = CurrentCost * 2.5-5.0` (adjustable per draw based on meta)
- Player draws 3 random upgrades, picks 1
- Picked upgrade is added to active pool
- Upgrades stack additively or multiplicatively (defined per upgrade)

### Rarity Tiers

**Common (60% chance)**: Small incremental buffs
- "+10% Code Editor efficiency"
- "-5% Tech Debt accumulation"
- "+15% LOC generation"
- Safe, predictable choices

**Uncommon (30% chance)**: Medium buffs with trade-offs
- "+30% building production, but +20% costs"
- "-30% tech debt, but buildings produce slower"
- "Stack 3x for major bonus"
- Interesting decisions

**Rare (9% chance)**: Paradigm shifts
- **"Functional Programming"**: 1.5x multiplier on Code Editors, stackable
- **"OOP Architecture"**: Buildings scale better with count (+0.5x per 10 owned)
- **"Microservices"**: Buildings boost each other, but base costs +50%
- **"YOLO Deployment"**: -20% tech debt per stack (can go negative!)
- Game-changing build paths

**Legendary (1% chance)**: Broken modifiers
- **"Recursive Refactoring"**: Buildings evolve into stronger versions over time
- **"Infinite Recursion"**: Logarithmic scaling removed from one building type
- **"God Mode IDE"**: Manual LOC generation multiplied by building count
- Meme builds for absurd fun

### Stacking Rules

**Additive Stacks** (most upgrades):
```
Base + (UpgradeValue * StackCount)
Example: "+10% per stack" at 5 stacks = +50% total
```

**Multiplicative Stacks** (paradigm shifts):
```
Base * (UpgradeValue ^ StackCount)
Example: 1.5x at 3 stacks = 1.5³ = 3.375x total
```

**Evolution Tiers** (rare mechanics):
```
3x "Linter" → "Static Analysis Suite" (better bonus)
5x "Pair Programming" → "Mob Programming" (exponential bonus)
10x "YOLO Deployment" → "Production Chaos Theory" (negative tech debt gives bonus)
```

### Example Build Paths

**"Functional Purist"**
- Draw: Functional x3, CI/CD x2, Linter x5
- Result: 3.375x Code Editor output, -30% tech debt, evolved Linter
- Strategy: Stack Code Editors, ignore other buildings

**"Microservices Chaos"**
- Draw: Microservices x2, Remote First x4, Kubernetes x8
- Result: Buildings boost each other by 40% each, major synergy
- Strategy: Diversify, each building type makes others better

**"YOLO Meme"**
- Draw: YOLO Deployment x10
- Result: Tech debt goes so negative it becomes a production bonus
- Strategy: Rush everything, embrace chaos

## Tech Debt Mechanic

### The Tension System

**Accrual**:
- Every building purchase adds tech debt based on building tier
- "Hacky" buildings (low-tier, rushed) add more debt
- Buying "too fast" (e.g., >3 purchases in 10s) adds bonus debt
- Certain upgrades ("No Tests", "Ship It") increase accrual rate
- Architectural mismatches add debt (e.g., OOP build buying Functional upgrade)

**Penalties**:
- Each tech debt point = -1% total production
- Applies globally to all resources
- Can stack to devastating levels (-50% = half production)

**Resolution**:
- Refactoring action: Pay LOC + time to reduce debt
- Cost scales exponentially with debt amount
- Certain upgrades reduce debt ("CI/CD", "Tests", "Code Review")
- Some builds eliminate debt entirely (YOLO stacking)

**Strategic Depth**:
- Do I rush growth now and pay debt later?
- Can I afford to wait for the refactoring timer?
- Should I invest in debt-reduction upgrades?
- Is this build path sustainable long-term?

## Prestige & Meta-Progression

### The Reset Cycle

**Victory Condition**: Reach X Users (e.g., 10K, 100K, 1M scaling)
**Prestige Action**: "Sell Company, Start New Product"

**Meta-Currency**: "Reputation" or "Entrepreneur Score"
- Earned based on Users reached before prestige
- Formula: `Currency = Users ^ 0.5 * Prestige Tier Multiplier`
- Spend on permanent upgrades

**Meta-Upgrades**:

**RNG Quality** (most impactful):
- "+5% rare upgrade chance" (stacks to max 30%)
- "+2% legendary upgrade chance" (stacks to max 10%)
- Shifts risk/reward of drawing early

**Starting Bonuses**:
- "+100 starting LOC" (linear)
- "+1 free Code Editor" (linear)
- "+1 starting upgrade draw" (exponential)

**Quality of Life**:
- "Unlock Advanced Buildings" (new buildings in pool)
- "Unlock Tech Debt Mastery" (new debt reduction upgrades)
- "Faster Refactoring" (reduce refactoring time)

**Specialization Paths**:
- "Startup Mode": Better early scaling, weak late game
- "Enterprise Mode": Slower start, massive late game potential
- "Open Source": More upgrade variety, slower prestige
- "Acquisition Path": Multiple prestige exits with unique bonuses

## Roguelike Elements

### Run Variance

**What Makes Each Run Different**:
1. Random upgrade draws force adaptation
2. Must optimize for synergies you actually get
3. Early legendary can define entire run
4. Bad draws = creative problem-solving

**Strategy Examples**:

**"Lucky Functional"**: Drew Functional x2 early
- Commit to Code Editor stacking
- Ignore buildings that don't synergize
- Focus on upgrade draws that boost manual generation

**"Cursed OOP"**: Drew OOP but got Microservices penalties later
- Hybrid architecture is inefficient
- Must balance conflicting paradigms
- Tech debt will spike
- Prestige earlier than optimal

**"Jack of All Trades"**: No paradigm shifts, only common/uncommon
- Safe, consistent progress
- No explosive power spikes
- Reliable prestige timeline
- Boring but effective

### Replayability Hooks

1. **Build Discovery**: "What happens if I stack X upgrade 10 times?"
2. **Challenge Runs**: "Can I prestige with only common upgrades?"
3. **Speed Optimization**: "What's the fastest 10K users run?"
4. **Meta-Strategy**: "Do I prestige now or grind for one more rare?"
5. **Achievement System**: Unlock special modes, modifiers, rare pool additions

## Data Structures

### Future Implementation

```go
// Upgrade system
type Upgrade struct {
    ID          string
    Name        string
    Description string
    Rarity      UpgradeRarity // Common/Uncommon/Rare/Legendary
    Effect      UpgradeEffect
    Stacks      bool
    MaxStacks   int // 0 = unlimited
}

type UpgradeRarity int

const (
    RarityCommon UpgradeRarity = iota
    RarityUncommon
    RarityRare
    RarityLegendary
)

type UpgradeEffect struct {
    Type       string  // "multiplier", "flat", "techDebt", "special"
    Target     string  // "codeEditor", "allBuildings", "LOC_generation"
    Value      float64
    IsAdditive bool
    StackType  string  // "additive", "multiplicative", "evolve"
}

type UpgradeShop struct {
    DrawCost        float64
    DrawCount       int
    CostMultiplier  float64 // 2.5-5.0, dynamic based on meta
    AvailablePool   []Upgrade
    ActiveUpgrades  map[string]int // ID -> stack count
    RarityWeights   map[UpgradeRarity]float64
}

// Tech debt system
type TechDebt struct {
    Current      float64
    AccrualRate  float64 // Per purchase
    PenaltyRate  float64 // -1% production per point
    RefactorCost float64
    RefactorTime time.Duration
}

// Prestige system
type PrestigeBonus struct {
    ID           string
    Name         string
    Cost         float64
    Unlocked     bool
    Level        int // For stackable bonuses
}

type PrestigeState struct {
    Reputation       float64
    TotalPrestiges   int
    PurchasedBonuses map[string]int // ID -> level
    AvailableBonuses []PrestigeBonus
}

// Expanded GameState
type GameState struct {
    Resources     map[string]float64
    Buildings     map[string]Building
    ActiveTimers  []Timer
    UpgradeShop   UpgradeShop
    TechDebt      TechDebt
    Prestige      PrestigeState
    RunStats      RunStatistics
}

type RunStatistics struct {
    StartTime    time.Time
    FeaturesBuilt int
    MaxUsers     float64
    TechDebtPeak float64
    UpgradesDrawn int
}
```

## Balance Philosophy

### Core Principles

1. **No Dominant Strategy**: Every build path should have viable endgame
2. **Meaningful Choices**: Every purchase/upgrade should feel impactful
3. **Risk/Reward**: More powerful options come with trade-offs
4. **Progressive Complexity**: Early game simple, late game intricate
5. **Prestige Is Progress**: Reset should feel like advancement, not loss

### Tuning Parameters

**Critical Balances**:
- Building cost scaling vs. production scaling
- Upgrade draw costs vs. upgrade power levels
- Tech debt accrual vs. refactoring costs
- Prestige currency gain vs. meta upgrade costs

**Adjustment Philosophy**:
- Always err on side of "too powerful" initially
- Better to be broken-fun than balanced-boring
- Add restrictions/complications later if needed
- Let players discover broken builds (it's a feature)

## Notes & Inspiration

**Design Influences**:
- **A Dark Room**: Minimalist, discovery-driven idle game
- **Universal Paperclips**: Exponential growth with meaningful choices
- **Kittens Game**: Deep incremental with multiple resource types
- **Slay the Spire**: Roguelike with synergistic build paths

**Unique Angle**:
- Software development theme adds flavor without complexity
- Tech debt creates actual resource tension
- Architectural choices (OOP vs Functional) provide thematic depth
- Upgrade stack abuse enables absurd optimization fun

**Core Innovation**:
- Roguelike randomness in incremental gameplay
- Tech debt as both mechanical and thematic system
- Stackable upgrades creating exponential build variety
- Prestige tied to strategic choices, not just grinding
